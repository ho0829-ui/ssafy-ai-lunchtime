# PRD Feature

짧고 모호한 기능 요청을 받았을 때, 바로 구현에 들어가지 않고 PRD(Product Requirements Document)를 먼저 정리하기 위한 스킬입니다.

## 왜 필요한가

"로그인 기능 추가해줘" 같은 한 줄짜리 요청은 겉보기엔 단순해 보이지만, 실제로는 소셜 로그인 여부, 세션 유지 방식, 실패 시 동작, 기존 회원 시스템과의 관계 등 결정해야 할 것이 많습니다. 이런 결정을 코드를 짜면서 즉흥적으로 내리면 나중에 "이게 아닌데" 하고 다시 만드는 일이 잦아집니다. 몇 분 들여 질문하고 PRD로 합의하면, 구현은 훨씬 빠르고 재작업이 줄어듭니다.

## 언제 이 스킬을 건너뛰어도 되는가

다음 중 하나라도 해당하면 질문 없이 바로 구현으로 넘어가세요:
- 요청 자체가 이미 충분히 구체적임 (예: 함수 시그니처, 입출력 형식, 엣지 케이스까지 명시된 경우)
- 사용자가 명시적으로 "바로 코드 짜줘", "PRD 생략", "일단 대충" 등으로 스킵을 요청
- 오타 수정, 리팩터링, 버그 수정처럼 애초에 "새 기능"이 아닌 작업
- 이미 이 대화 안에서 같은 기능에 대한 PRD 합의가 끝난 경우 (중복 질문 금지)

## 진행 순서

### 1단계 — 모호한 지점 파악

요청을 읽고 아래 항목 중 답이 없는 것을 찾습니다. 전부 다 물어볼 필요는 없고, **실제로 애매해서 구현 방향이 갈리는 항목만** 골라 질문하세요. 이미 요청이나 이전 대화에서 답이 나온 항목은 다시 묻지 않습니다.

- **목적/배경**: 이 기능이 왜 필요한가, 어떤 문제를 해결하는가
- **대상 사용자**: 누가 이 기능을 쓰는가 (일반 사용자, 관리자, 내부 시스템 등)
- **핵심 시나리오**: 사용자가 이 기능으로 정확히 무엇을 하게 되는가 (구체적인 흐름 1~2개)
- **입력/출력**: 어떤 데이터를 받고 어떤 결과를 내는가
- **성공 기준**: 이게 되면 "완료"라고 볼 수 있는 기준이 무엇인가
- **예외/실패 케이스**: 잘못된 입력, 실패, 권한 없음 등 예외 상황에서 어떻게 동작해야 하는가
- **범위 제외 (Out of scope)**: 이번에는 굳이 안 해도 되는 것 (다음 버전으로 미룰 것)
- **제약 조건**: 기존 코드/디자인/일정과 관련해 지켜야 할 제약이 있는가

### 2단계 — 질문하기 (한국어)

AskUserQuestion 도구를 사용해 한 번에 묶어서 질문하세요. 한 번에 하나씩 왔다갔다 하면 사용자가 지칩니다. 질문은:
- 최대 3~4개까지만, 실제로 구현 방향을 바꿀 만큼 중요한 것부터
- 각 질문에는 합리적인 기본값/추천 옵션을 하나 포함해서 사용자가 고민 없이 고를 수 있게 함
- 전문 용어는 풀어서 설명 (사용자가 비개발자일 수도 있음을 염두에 둠)

질문이 애매하거나 선택지로 만들기 어려운 항목(예: 자유 서술이 필요한 "목적/배경")은 AskUserQuestion 대신 대화 텍스트로 자연스럽게 물어봐도 됩니다.

### 3단계 — PRD 작성

답을 받으면 아래 템플릿으로 PRD를 정리해서 사용자에게 보여주고 확인을 받습니다. 파일로 저장해 달라는 요청이 없으면 대화 안에 바로 작성하고, 저장을 원하면 프로젝트 안에 적절한 위치(예: `docs/prd/`)를 사용자와 합의해 저장하세요.

```markdown
# PRD: {기능 이름}

## 배경 및 목적
{왜 이 기능이 필요한지, 어떤 문제를 해결하는지}

## 대상 사용자
{누가 사용하는가}

## 핵심 시나리오
1. {사용자가 겪는 구체적인 흐름}
2. ...

## 요구사항
- {구체적이고 검증 가능한 요구사항 목록}

## 입력 / 출력
- 입력: {...}
- 출력: {...}

## 예외 처리
- {상황}: {기대 동작}

## 성공 기준
- {이 기준이 충족되면 완료로 간주}

## 범위 제외 (Out of scope)
- {이번 작업에서는 다루지 않는 것}

## 제약 조건 / 참고사항
- {있다면}
```

빈 항목이 있어도 괜찮습니다 — 정보가 없으면 "미정" 또는 사용자와 논의한 가정을 명시하고, 억지로 채우지 마세요.

### 4단계 — 확인 후 구현

PRD를 보여준 뒤 "이대로 진행할까요?"라고 확인을 받으세요. 사용자가 수정을 요청하면 반영하고, 승인하면 그때 구현을 시작합니다. PRD 없이 바로 코드부터 작성하지 마세요 — 이 스킬의 핵심은 순서를 지키는 것입니다.

## 주의할 점

- 질문은 실제로 구현 방향에 영향을 주는 것만 하세요. 형식적인 질문 세례는 오히려 사용자를 지치게 합니다.
- 사용자가 이미 답을 준 항목을 다시 묻지 마세요.
- 이미 비슷한 기능이 코드베이스에 있다면, 질문하기 전에 먼저 코드를 훑어보고 기존 패턴을 참고해서 질문 수를 줄이세요 (예: 기존 인증 방식이 있으면 "로그인 방식"을 다시 묻지 않아도 됨).
- PRD는 무겁게 만들 필요 없습니다. 간단한 기능이면 PRD도 몇 줄이면 충분합니다.
